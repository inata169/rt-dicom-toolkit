# RT DICOM Toolkit AI Agent Rules

This document is the provider-neutral development policy for Codex, Claude Code,
Antigravity, and other coding agents. Existing code, documentation, tests, and
human-approved OpenSpec changes are repository evidence. If they conflict, do
not reconcile them by inference: preserve the current state and evidence, then
report the conflict to a human.

This repository uses AI inside an engineering harness with explicit boundaries,
validation, and stopping conditions. Keep the bounded inner loop, which may fix
safe failures, separate from the outer loop, which returns specification,
medical, privacy, and scope decisions to a human.

## 1. Scope and safety position

- `rt-dicom-toolkit` supports radiotherapy DICOM anonymization, validation of
  anonymization results, template synchronization, and offline installation.
- Do not claim that this software alone guarantees complete de-identification,
  legal or organizational compliance, clinical suitability, patient QA, or
  device or vendor certification.
- Do not change DICOM attributes, UID reference relationships, file-meta
  information, transfer syntax, or RT object structure outside an approved task.
- Do not declare data safe or non-reidentifiable only because it passed this
  toolkit's anonymizer or validator.
- Do not add safety, compatibility, or clinical claims to public documentation,
  the UI, logs, or reports unless existing tests support them.

## 2. Protected data and material

Do not add, generate, copy, or commit any of the following to the repository:

- real-patient DICOM, images, metadata, UIDs, derivatives, or reidentifiable
  fragments;
- inputs, anonymized outputs, validation reports, logs, or screenshots that
  contain real-patient data;
- configuration or identifiers specific to a real institution, machine,
  vendor, or research participant;
- credentials, tokens, passwords, private keys, or populated `.env` files;
- configuration or instructions containing a personal-computer absolute path;
- bundled Python runtimes, wheels, generated ZIP files, or other third-party
  redistributables whose license has not been reviewed; or
- material from a private repository that a human has not approved.

Development and CI must use DICOM generated by tests or human-reviewed,
project-authored synthetic samples. A derivative of real-patient data is not
synthetic merely because it has been anonymized.

Do not weaken `.gitignore` protections for DICOM, reports, logs, or distribution
artifacts. Before tracking a new DICOM file, present evidence that it is
synthetic, list all attributes it contains, document its license and necessity,
and obtain explicit human approval. Never bypass this boundary with
`git add -f`.

## 3. Questions for the primary user

Every direct question to this repository's primary user should normally be
answerable with `yes` or `no`. State the observed evidence and necessary context
first, make one safe concrete proposal, and end with the equivalent of
"May I proceed with this proposal? yes/no".

- Do not combine independent choices, permissions, paths, or external actions
  in one question.
- When several options exist, recommend the smallest safe option first. A `no`
  does not approve a different option.
- When a free-form value is needed, derive and propose one safe value for
  confirmation.
- A `yes` authorizes only the action and scope stated in that question. Silence
  or ambiguity is not consent.
- Do not weaken an unresolved specification, medical, privacy, or safety issue
  merely to force it into a binary question.

Status and completion reports do not need to end with a question.

## 4. Real-patient data and external execution

Anonymization, validation, GUI operation, performance measurement, or log
analysis involving real-patient DICOM is allowed only when a human explicitly
requests that data and exact operation. Even then, keep the data and all output
outside the repository, handle only the minimum necessary files, and do not copy
their contents into chat, screenshots, test fixtures, or logs.

Do not discover, mount, connect to, or run against patient datasets, shared
folders, DICOM servers, medical devices, or external tools on an agent's
initiative. Normal development, CI, and offline-installation tests use synthetic
data, mocks, and fake runners.

## 5. Inner AI loop

An agent may automatically correct only failures caused by the current diff in
these groups:

- Python syntax, compilation, lint, type, or configuration-format errors;
- focused pytest failures directly associated with the change;
- external-tool contract tests that use synthetic data or mocks;
- document formatting, link, encoding, line-ending, or trailing-space defects;
  and
- an unambiguous regression caused by the current diff.

For one failure group, make at most three correction attempts and rerun the same
focused validation after every attempt. Stop earlier when any of these conditions
is met:

- the same failure occurs twice;
- the error count, delta, or unresolved scope does not shrink;
- passing would require disabling a test, hard-coding a bypass, or weakening
  validation;
- it is unclear whether the specification, test, fixture, or reference data is
  wrong; or
- an out-of-scope change, real data, external connection, or additional
  permission would be required.

Keep the observed failure, minimal change, and validation result for each
attempt. Do not delete, conceal, or reword failed evidence into a success.

## 6. Outer human loop

Do not decide any of the following automatically. Report the observation,
current diff, completed validation, remaining uncertainty, and smallest required
decision, then stop:

- a public-scope, requirement, OpenSpec, or architecture change;
- a change to tags that are anonymized or retained, private-tag handling, or PHI
  detection rules;
- a change to UID generation, mapping, reference replacement, patient-ID
  mapping, or date handling;
- a change to DICOM coordinates, geometry, units, dose, MU, normalization, or
  the meaning of RTPLAN, RTSTRUCT, or RTDOSE;
- a change to file-meta information, transfer syntax, SOP Class, or DICOM
  conformance;
- a decision about clinical suitability, anonymization guarantees, legal
  compliance, patient QA, or vendor approval;
- work involving patient-, institution-, machine-, or vendor-specific data;
- execution against real-patient data or an operational environment;
- destructive operations, out-of-scope writes, permission expansion, or scope
  expansion; or
- any need to weaken a guard, test, audit, validation, or `.gitignore`
  protection.

## 7. OpenSpec change management

Before changing runtime code for a new capability, public-behavior change,
architecture change, substantial dependency change, data-handling boundary
change, or other scope expansion, inspect `changes/`.

- Start from `changes/_template.md` and use a unique numbered, verb-led change.
- Record the background, in-scope and out-of-scope work, requirements,
  acceptance criteria, validation, and risks.
- Describe deltas with successful and failure scenarios.
- Do not implement until a human changes the status to `✅ APPROVED`.
- Keep the task checklist aligned with real progress. Never mark incomplete or
  unverified work complete.
- At completion, record acceptance and validation results. The current
  `changes/` directory retains history; do not move or delete changes until the
  repository adopts an approved archive convention.

A bug fix that restores documented behavior, a documentation correction that
does not change runtime behavior, or an unambiguous typo does not require a new
proposal. A human may explicitly waive or defer OpenSpec for a specific task.
OpenSpec approval never overrides protected-data, real-patient-data, clinical,
or permission boundaries.

## 8. Pull-request stopping rule

Completion means satisfying the human-approved scope and acceptance criteria
and passing required validation; it does not mean exhausting all possible
improvements. At that point, stop expanding the pull request or adding unrelated
refactors and future capabilities.

- Make an additional correction only for a concrete merge-blocking defect in
  the current diff.
- A merge blocker is a safety, security, or privacy exposure; an approved
  requirement violation; a required-validation failure; or an unambiguous
  regression.
- Verify a reviewer severity label against the code and approved scope; the
  label alone is not authority.
- Allow at most one minimal review-driven correction round on the same branch
  and pull request.
- Robustness ideas, optional coverage, style, unrelated refactors, and future
  capabilities do not block the current pull request.
- Do not create a tracking issue, branch, pull request, OpenSpec change, or
  automation unless a human requests it.
- An agent does not merge. Report evidence that the change is ready and leave
  the merge decision to a human.

If the final correction round reveals another possible blocker, report it
instead of starting a recursive review loop.

## 9. Environment, permissions, and Git

- Prefer procedures reproducible on Windows 10/11 PowerShell and Ubuntu 24.
- Store text as UTF-8. Use `PYTHONUTF8=1` when needed. Do not create translation
  logs or temporary encoding files unless an encoding failure is observed.
- Keep the project usable on low-specification computers: avoid heavy resident
  processes, excessive parallelism, and unnecessary large dependencies. Start
  with focused checks and divide work into small steps.
- Default to repository-scoped writes. Obtain specific approval for network
  access, extra permissions, or additional write locations.
- Do not add Docker socket access, privileged containers, host networking,
  credentials, or broad writable roots by default.
- At the start of work, inspect the repository root, branch, status, recent
  history, remote, and tags. Preserve unrelated user work.
- Make runtime and documentation changes on a feature branch. Do not commit or
  push directly to `main`.
- Do not force-push, rewrite history, modify tags, publish releases, or merge
  pull requests automatically.
- Do not use `stash`, `reset --hard`, forced deletion, or bulk untracked-file
  deletion to hide or discard existing work.
- Commit, push, and create a pull request only within the approved task and the
  repository's handoff procedure.

## 10. Validation and completion reporting

Run checks focused on the change first, then all applicable public checks:

```text
python -m compileall rt_dicom_toolkit
python -m pytest -q -p no:cacheprovider tests
python tools/offline_smoke_test.py
git diff --check
git diff --stat
git status --short
```

- For documentation-only changes, run at least `git diff --check`, reference
  checks, `git diff --stat`, and `git status --short`, and state why runtime
  tests were omitted.
- For GUI changes, report automated tests, launch checks, and any visual items
  that could not be verified.
- For offline-installation changes, validate with synthetic DICOM and record the
  Windows target, artifact origins, and licenses.
- Never use real-patient data for validation. If a test expects real data,
  report the skip reason and do not search for the data.

The completion report must list changed files, exact commands and results,
unrun checks and reasons, unresolved items, and branch plus commit or pull
request identifiers when created. It must also state whether runtime behavior,
the public specification, DICOM meaning, or protected data changed.
